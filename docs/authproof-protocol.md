# Auth-proof protocol

How this service authenticates requests, and why it can stream 200 MiB bodies. This
replaced the BRC-103/104 mutual-auth middleware: no handshake, no session state, no signed
response envelope, no `/.well-known/auth` route.

## The proof

Every authenticated request carries one header:

```
X-Bsv-Auth: base64(JSON)
```

where the JSON is:

```json
{
  "action":      "POST /v1/log/<deviceId>?seq=1&generation=1 sha256=<hex>",
  "identityKey": "<caller's compressed public key, DER hex>",
  "expiresAt":   1755700000000,
  "nonce":       "<base64 of 32 random bytes>",
  "signature":   "<base64 of DER ECDSA signature>"
}
```

The signature is created exactly as the published `@bsv/auth` npm package does
(`createAuthProof`): the signed bytes are the UTF-8 of

```
action \n identityKey \n expiresAt \n nonce
```

signed with `wallet.createSignature` under BRC-42/43 derivation:

- `protocolID`: `[2, "backup cache auth"]`
- `keyID`: the nonce
- `counterparty`: the other side's identity key (the server's when signing, the
  claimed `identityKey` when verifying)

`expiresAt` is Unix **milliseconds** (JS `Date.now()` convention). Validity window is
2 minutes with 30 seconds of clock-skew tolerance, matching `@bsv/auth` defaults.
`internal/authproof/testdata/vectors.json` is generated by the TypeScript package and
pins Go/TS byte compatibility (regenerate with `test-client/genvectors.mjs`).

Clients learn the server's identity key from unauthenticated `GET /v1/limits`
(`serverIdentityKey`), alongside the blob cap (`maxBlobBytes`).

## The action string

```
<METHOD> <request-URI>                      for bodyless requests
<METHOD> <request-URI> sha256=<body hex>    for uploads
```

`request-URI` is the literal path-plus-query as sent on the wire — no re-encoding, no
parameter sorting. Both sides use the same string, so no canonicalization pass exists to
get wrong. Binding the method and full URI means a proof minted for one request cannot be
replayed against any other route, sequence number or generation; the nonce store refuses
the same proof twice even on its own route.

## Why the body's hash, not the body

Signing the body itself (as `@bsv/auth`'s optional `body` binding does) forces the
verifier to hold the full body before any byte can be trusted — that is the buffering
this design removes. Signing a trailing signature after the body was rejected too: it
means writing ciphertext to storage before the sender is authenticated.

Instead the proof signs the body's sha256 inside the action string. The order on the
server is:

1. Size guard: an oversize body is answered 413 before auth is even attempted.
2. Verify the proof from the header — shape, action match, freshness, signature — and
   consume the nonce. The sender is now authenticated; not one body byte has been read.
3. Stream the body into the store in bounded chunks, hashing as it goes, inside one
   transaction.
4. At EOF, compare the computed hash with the digest the proof signed. A mismatch aborts
   the transaction: `400 ERR_BODY_DIGEST_MISMATCH`, and nothing is kept.

A forged body therefore costs the attacker an upload and a rollback, never storage, and
the server's memory use is constant regardless of blob size.

## Failure responses

| Case | Status | Code |
|---|---|---|
| Missing/malformed/expired/invalid proof, wrong action, replayed nonce | 401 | `ERR_AUTH_REQUIRED` |
| Upload proof without a `sha256=` digest | 401 | `ERR_AUTH_REQUIRED` |
| Body does not hash to the signed digest | 400 | `ERR_BODY_DIGEST_MISMATCH` |
| Body over the cap (answered before auth) | 413 | `ERR_BLOB_TOO_LARGE` |

Responses are not signed. Transport integrity is TLS's job; the payloads themselves are
ciphertext the server cannot read, and every stored blob's sha256 is reported on upload
and in the index for end-to-end verification.
